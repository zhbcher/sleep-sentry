# 算法金标准测试结果（2026-10-03）

算法在**合成音频**上验证，Python 参考实现与 Kotlin 生产实现结果一致。
真实数据验证（PhysioNet AIMS 配对）尚未做，见「待办」。

## 验收线

| 指标 | 目标 | 实测 |
|---|---|---|
| 事件召回 | ≥90% | **100%**（7/7 组） |
| 计数准确率 | ≥95% | **100%**（7/7 组） |
| 起点误差（中位） | ≤0.5s | **0.04–0.18s** |
| 起点误差（最大） | — | 0.16–2.38s（噪声环境离群） |

判定 `PASS` 需要同时满足召回、计数准确率、起点误差中位三条。

## 分场景实测

| 场景 | 真值/检出 | 起点误差中位 | 起点误差最大 | 时长误差中位 |
|---|---|---|---|---|
| 基准-安静环境 | 8 / 8 | 0.07s | 0.16s | 0.08s |
| 基准-电视频繁 | 8 / 8 | 0.05s | 0.13s | 0.07s |
| 高噪声环境(3x) | 6 / 6 | 0.17s | **2.38s** | 0.09s |
| 高事件密度 | 12 / 12 | 0.07s | 0.16s | 0.05s |
| 极安静环境(0.5x) | 10 / 10 | 0.04s | 0.05s | 0.06s |
| 嘈杂+电视(2x,6段) | 10 / 10 | 0.09s | 0.57s | 0.02s |
| 长夜1小时-混合 | 15 / 15 | 0.07s | 0.51s | 0.06s |

**噪声越大，静默边界越模糊**（3x 噪声下最大误差 2.38s）。这是方法本身的性质：
环境噪声会持续把鼾声的尾巴垫高，"声音消失的时刻"本身就不精确。
安静房间（实际使用场景）误差在 0.05–0.2s。

## 调试过程中踩到的坑（都已修，改代码前先读）

| 坑 | 现象 | 根因 |
|---|---|---|
| deque 游标不同步 | 峰检测在 6.4 秒后彻底停摆 | 裁剪历史缓冲时没把 `_pk_i` 一起回退，下标越界后 while 循环再��不执行 |
| 上下文张冠李戴 | 突出度算错 | `before` 和 `after` 都指向 `db[1:11]`（同一段），且 deque 从左弹出把"峰之前的上下文"丢光 |
| 确认竞态 | 8 个事件只检出 2 个 | 峰检测有 1s 前瞻，而确认逻辑在静默结束后 1.0s 就去查峰，等它到时喘息已结束 —— 等候时间必须覆盖 `EVENT_CTX_S + PEAK_CTX_S` |
| 对称去抖动 | 召回从 95% 掉到 62% | "转有声"也要求 0.5s 连续，而恢复性喘息只有 0.2s 高 SNR。**去抖必须不对称：转有声要短(0.2s)、转静默要长(0.6s)** |
| 去抖引入计时偏移 | 时刻整体晚 0.5s | 状态切换时才计算阈值穿越点。**穿越时刻要在"运行开始"那一刻就记下来** |
| 真值定义自相矛盾 | 明明有声音却判为静默 | 合成器把"鼾声→暂停"之间的 3–9s 自然间隙算在暂停之外，真值起点比真实静默晚 5–6s |
| 指数衰减尾巴 | 计时误差被放大到 1.4s | 鼾声数组写完后仍有残能量。**真值端必须加淡出让边界物理明确** |
| 电视造出的假静默 | 凭空多出 16s 事件 | 电视段戛然而止→16s 无人打鼾→下一段电视又"响"起来被当成恢复性喘息 |
| 合成器不现实 | 测出的"误报"其实是数据问题 | ①电视叠在暂停上 ②电视段互相重叠 ③电视两段之间夹纯安静。真实房间电视是连续背景音，不会围着呼吸开关 |

## 已知局限（写在报告与文档里，不藏着）

1. **不重度打鼾的人群漏报率高** —— 方法靠"鼾声消失"观测气流中断，无鼾声则无信号。
2. **中枢性呼吸暂停检测不到** —— 无鼾声恢复期，与"安静睡觉"声音上无法区分。
3. **恒定环境噪声（风扇/空调嗡鸣）会掩盖鼾声** —— 这类噪声在能量上与"安静"无法区分。
4. **环境噪声的突变可能被误计为事件** —— 已加"恢复性喘息必须是瞬态"判据压制，
   但无法完全消除；报告提供原声回放让用户自行判断。
5. **超过 60 秒的静默一律不算事件** —— 更可能是人起身/翻出麦克风/录音中断。
6. 计时精度随环境噪声下降（见上表）。

# 真实数据验证：APSAA（2026-10-03 追加）

## 数据集

| 项 | 内容 |
|---|---|
| 名称 | Audio-Polygraphy Dataset for Sleep Apnea Analysis (APSAA) |
| 来源 | Zenodo record 14096541，**CC-BY 4.0** |
| 内容 | 32 名受试者整夜录音（WAV，含鼾声）+ 同步多导睡眠图 + 人工事件标注 |
| 采样率 | **4000 Hz 单声道 16bit**（不是手机常见的 16/44.1 kHz） |
| 标注类型 | Snore / Obstructive Apnea / Central Apnea / Mixed Apnea / Hypopnea / No Effort / Desaturation |
| 规模 | 29457 个事件；其中 Obstructive+Mixed Apnea 5082 次 |
| 本地路径 | `sleepsentry/data/APSAA.zip`（3.93 GB，不入库） |

评估脚本：`dsp/run_apsaa.py`、`dsp/run_apsaa_sweep.py`

## 结果：方法在这份数据上失效了 —— 但原因不是算法

### 默认阈值下的表现（前 2 夜）

| 指标 | 结果 |
|---|---|
| 召回 | 39.5%（17/43） |
| **精确** | **2.9%（17 命中 vs 563 误报）** |
| AHI 真值 / 估算 | 4.2 / 48.0（严重高估） |

### 阈值扫描（6 夜，294 个真值事件）

| SNR_ON | SNR_OFF | 召回 | 精确 | F1 | AHI误差 |
|---|---|---|---|---|---|
| 1.5 | -1.0 | 1.4% | 50.0% | 2.6% | -6.6 |
| 2.5 | 0.0 | 9.9% | 41.4% | 15.9% | -5.2 |
| **3.0** | **0.5** | **35.4%** | **36.1%** | **35.7%** | -0.2 |
| 4.0 | 1.5 | 54.8% | 22.3% | 31.7% | +9.7 |
| 6.0 | 3.5 | 66.0% | 16.2% | 26.0% | +20.7 |
| 8.0 | 5.5 | 69.7% | 13.5% | 22.6% | +28.0 |

**最佳 F1 仅 35.7%**，远低于文献报告的 0.79/0.80。

### 根因排查：录音里没有可用的鼾声信息

| 检查项 | 结果 | 判读 |
|---|---|---|
| 音频包络 vs 鼻导管鼾声包络 相关系数 | **-0.012** | 近乎完全不相关 |
| 鼾声段 SNR 中位 vs 其余时间 | 3.8 dB vs 1.6 dB | 余量仅 2.2 dB |
| 50–150 Hz 可分性（效应量） | 0.70 | 低于 0.8 可分线 |
| 150–300 Hz | 0.70 | 同上 |
| 300–600 Hz | 0.67 | 同上 |
| 600–1000 Hz | 0.66 | 同上 |
| 1000–1900 Hz | 0.59 | 同上 |

**结论：五个频带全部不可分，音频与临床鼾声标注不相关 —— 这份录音的麦克风离患者太远，房间里没有录到可用的鼾声信息。**
任何检测器（包括 DNN）在这份数据上都接近随机，35.7% 的 F1 已接近该数据集的信息上限，不是调参问题。

### 与文献的差距在哪

| | APSAA | 谢菲尔德论文 | 手机放床头（本项目目标场景） |
|---|---|---|---|
| 麦克风位置 | 病房房间内 | **床头，30–50cm** | **床头，30–50cm** |
| 采样率 | 4 kHz | 16 kHz | 16 kHz |
| 方法 | 规则（本文） | DNN + 30s 窗口 | 规则（本文） |
| 效果 | F1 36% | 敏感度 0.79 / 特异度 0.80 | **未验证** |

文献的高数字来自**麦克风足够近**的录音，不是来自算法本身。
本项目的目标场景（手机放床头）与谢菲尔德的布置更接近，因此那份 0.79 仍是最相关的外部证据 ——
但**在本项目上它尚未被复现过**。

### 试过并否决的运行时质量门限（三次，全部被实测证伪）

曾想把"录音能不能用"做成自动门限，让 App 在数据不可用时拒答。三次尝试：

| # | 门限思路 | 实测 | 结论 |
|---|---|---|---|
| 1 | 有声帧 SNR 中位数 ≥8dB | APSAA 全部 10 夜 **放行**（8.4–12.6 dB） | 无效 |
| 2 | Cohen's d（有声组 vs 静默组） | 1.27–1.63，全部放行 | **循环论证**：两组本身由阈值划分，当然分得开 |
| 3 | Cohen's d（最响 10% vs 中位数） | 3.7–10.0，全部放行 | 分组不再循环，但"响的时刻"可能是关门声/脚步声，不是鼾声 |

**根本困难：单夜无标注数据无法自证"响的那些声音是什么"。**
要做真正的判断，需要频谱形状分类器（有标注训练），或直接与家用监测仪配对实测。

最终处理：三次尝试的门限全部移除。第 3 个指标保留，但**如实改名为 `loudnessContrastDb`（响度对比度）**，
只作为诊断信息展示、**不参与质量门限**，并在代码注释与本文档里写明它不能代表检测能力。
`LoudnessContrastTest` 里有一条回归测试专门防止后人误用它。

## 线上崩溃：TimelineView 每次启动闪退（v1.0.1 修复）

**用户真机堆栈**：
```
java.lang.IllegalArgumentException: Cannot coerce value to an empty range:
  maximum 1072.0 is less than minimum 1073.0825
    at kotlin.ranges.RangesKt___RangesKt.coerceIn
    at com.sleepsentry.ui.TimelineView.onDraw(TimelineView.kt:94)
```

**根因**：
```kotlin
x2.coerceIn(x1 + 3f, w)      // ← x1 + 3f > w 时下界大于上界，直接抛
```
事件落在整夜最末尾时（`startSec / recordedSec ≈ 1`），`x1 + 3f` 超过画布宽度。

**为什么"前两次正常、之后一直崩"**：
第一次打开还没有记录 → 不画时间轴；某晚录出末尾事件后，
之后每次启动 `renderReport()` 都会 `setData` → `onDraw` → 每次都崩。
**不是随机问题，是确定性的、只要那份数据还在就必崩。**

**修复**：
1. 抽出纯函数 `TimelineGeometry.markBounds()`，不依赖 `coerceIn`，显式夹取并保证
   `0 ≤ left ≤ right ≤ width`
2. 触摸命中判定改用同一套几何，避免绘制与点击算出不同位置
3. `onDraw` 加兜底 try/catch：绘图异常降级为"图不出来"，不再带走整个 App
   （报告文字比图表重要）
4. 时间刻度数量限制在 1~24，防止异常数据拖慢绘制

**回归测试**（`TimelineGeometryTest`，9 条）：
崩溃现场数值逐位复现、末尾事件、零时长事件、负数/越界时间、终点早于起点、
退化输入（宽度 0/负宽）、NaN、绘制与命中共用几何，
外加 **2 万次随机扫描**（含负时长/负宽度/负时间）断言永不产生非法区间。

**教训**：纯函数 + 边界扫描测试，能在装机前抓住这类只在极端数据下才暴露的崩溃。
UI 代码同样需要，而且比 DSP 更容易出事 —— 因为脏数据比极端信号常见得多。

## v1.1.0 新增功能，以及测试抓到的两个真 bug

用户提了 4 条需求：存储配额、录音按时间排序、清除全部、每小时柱状图。

### 用户报的"排序混乱"——根因是文件名不含时间

旧文件名只带递增序号：`seg_2026-10-03_0001.pcm`。两个问题：

1. **事件要过约 5 秒才确认**，序号 ≠ 发生时间，顺序本身就对不上
2. **序号进位会倒序**：9999 → 10000 时字典序 `"10000" < "9999"`，
   按文件名排序整体反过来。一晚只要事件超过 9999 个（或将来索引变长）就必然错

**修复**：文件名改为 `seg_<yyyy-MM-dd>_<yyyyMMdd-HHmmss>_<序号>.pcm`，
带**事件发生的绝对时刻**，字典序 == 时间序，问题从根上消失。
另把报告页事件列表从"按憋气时长"改为**默认按时间**，并提供切换按钮。

### 测试抓到的两个真 bug（肉眼不可能发现）

| # | Bug | 后果 | 怎么发现的 |
|---|---|---|---|
| 1 | `HourlyBuckets` 用 `absMs / 3600000 % 24` 算钟点 | 拿到的是 **UTC 钟点**。北京时间用户凌晨 3 点的事件会被归到前一天 19 点，**整张柱子图全错** | 写跨午夜测试时断言失败 |
| 2 | `SegmentNaming.parseRecordedAt` 的正则 `"seg_(\d{8})-(\d{6})_"` | 日期段实际是 `2026-10-03`（带横线），正则要求 8 位数字，**永远匹配不上**，录音时刻一直静默退化成"文件修改时间" | 写"文件名序 == 时间序"测试时失败 |

另外 `coveredRange` 里那句"跨午夜时 endHour 拉回 23"的修正在改用本地钟点后**反而是错的**：
本地钟点下跨午夜本就是小时数变小（23 点睡到次日 6 点 → end=6 < start=23），
强行拉回 23 会把底纹画满一整圈。已删除，并新增 `isCovered()` 供图表处理跨午夜。

### 配额与清除的设计要点

| 项 | 决策 |
|---|---|
| 配额粒度 | **每晚**（用户原话"每天"），统计 JSON 永不删除 |
| 淘汰顺序 | 按**录音时刻**从旧到新，**不按文件名**（否则重犯上面的错） |
| 整夜音频 | **最后才删**。它是用户主动开的开关且单文件巨大，先动它会让"开了整夜留存却一晚都留不下" |
| 默认值 | 200MB/晚。默认模式（只留事件片段，约 3MB/晚）几乎用不到；开了整夜留存约存 2 晚 |
| 选项 | 50 / 100 / 200 / 500 / 1000 MB / 不限 |
| 清除 | 二次确认弹窗；删音频 + 历史报告，**保留监听开关与时段设置** |

### 柱状图

- 按**本地钟点**分 24 桶（睡眠跨午夜，用相对小时会错位）
- 浅蓝底纹标出当晚实际有录音的时段，跨午夜拆成两段画
- 颜色分档：1 次以下绿 / 1–3 黄 / 3 以上橙红
- 点柱子跳到该钟点最严重的事件并高亮 1.5 秒

### 测试

29 → **46 条**，新增 17 条覆盖配额淘汰顺序、整夜音频优先级、
文件名与时间序一致（含旧命名倒序的对照证据）、跨午夜分桶、本地时区口径。

## v1.2.0：日历 + 界面拆分 + 清除逻辑修正

### 用户反馈的三条

1. **"清除所有录音与记录"只该清录音，不清数据** —— 原实现把音频和历史报告一起删了。
   拆分出 `clearAllAudio()`（默认，主路径）与 `clearEverything()`（需二次确认的彻底清除）。
   **音频只是证据，统计（趋势、日历色块、分级）才是长期积累的价值**，一并删掉等于毁掉积累。
2. **日历色块** —— 每月一张，每天一格，颜色深浅 = 当晚严重程度。点某天看概要，可跳到报告页看完整内容。
3. **界面太长** —— 原先所有内容堆在一个 ScrollView 里。拆成底部导航四页：
   **状态 / 报告 / 日历 / 设置**，每页只放自己该有的东西。

### 日历色块分级（与报告页完全一致，不另立标准）

| 色 | 含义 | 判定 |
|---|---|---|
| 灰 | 无记录 | — |
| 浅灰 | 信号不足 | `!quality.ok`（优先于严重程度，避免让用户误以为"这天很糟"） |
| 绿 | 正常 | <5 次/小时 |
| 黄 | 轻度 | 5–15 |
| 橙 | 中度 | 15–30 |
| 红 | 重度 | >30 |

按**本地钟点**与跨午夜月份网格处理；跨午夜的底纹拆成两段画。

### 抽成纯函数以便测试

| 对象 | 作用 | 为什么要测 |
|---|---|---|
| `MonthGrid` | 月份网格数学（1 号是星期几、格号↔日期往返、月份跨年、点击命中） | **日历差一天用户一眼就看出来**，不能只靠肉眼验 |
| `DayStateMapper` | 记录 → 色块状态 | 分级口径必须与报告页一致，否则两处说法打架 |

测试里用真实 Calendar 交叉验证 4 年 × 12 月的"1 号是星期几"，
并对 3 年逐日做「格号 ↔ 日期」往返断言。

### 写测试时抓到的两个自己算错的地方

| 位置 | 我原本的预期 | 实际 |
|---|---|---|
| `shiftMonth(2026, 11, -25)` | 2023年12月 | 2024年11月（12+13=25） |
| `shiftMonth(y, m, 12)` | 同一年同月 | **明年的同一个月**（年份+1） |

两处都是测试预期算错，实现是对的 —— 但也说明月份数学确实容易搞错，
这正是要给它写测试的理由。
